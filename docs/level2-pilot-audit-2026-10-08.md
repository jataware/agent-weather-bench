The existing `weeks34-rainfall` Level 2 is a suitable small pilot of open forecasting research. The agent chooses a method, can request five controller-owned development scores, and submits a reproducible forecast evaluated against separate final observations. It already supplies the essential AIRS-like interaction without requiring a new task or a prescribed algorithm. This is a pilot of bounded experiment design and generalization, with modest demonstrated headroom on an already inspected historical split. It cannot establish a fresh forecasting capability boundary.

This audit used source code, existing JSON evidence and documentation only. It ran no scientific calculations, containers or models and changed no template. The selected instance is `final-2018-2021--all-cells`, spec version 4. Its current certification records fingerprint `453f237dafbfe0d3389eb0009d8cd485ccea6bbbcc672e18b87872ce907ce163`, passing automatic controls, with trial certification and scientific approval pending.

The scientific job is ordinary subseasonal postprocessing: predict 14-day CPC rainfall totals from CFSv2 ensemble-mean forecasts at nine southwest-US cells. Training targets close before 2015; development issues occupy 2015–2017 subject to the target-close boundary; final issues occupy 2018–2021. The final score covers 208 issues and nine cells. The source snapshot contains 1,194 complete issues. Both variables are already totals in mm, so neither needs conversion from a daily rate. The model may choose seasonal bias correction, regularization, pooling or combinations with climatology. It does not acquire raw global forecasts, fit a weather foundation model or reproduce an operational release archive. The [dataset paper](https://arxiv.org/abs/2109.10399) and [authors' toolkit](https://github.com/microsoft/subseasonal_toolkit) give relevant scientific context; full-US published scores do not become targets for this small subset.

The interaction resembles [AIRS-Bench](https://arxiv.org/html/2602.06855v1) in leaving methods open and separating accessible validation feedback from final grading. Its scale and evidence differ: AIRS used much larger compute/time budgets and repeated seeds. Our two attempts should answer whether agents can conduct useful bounded experiments here, rather than whether they reproduce those benchmark results. Ordinary library/API documentation is appropriate; controller references, control solvers, prior winning submissions and private score tables must stay outside the substrate. Keep the existing four-part envelope.

There is a checked attainable improvement, but it is small. Current certification gives the training-fitted seasonal-harmonic-plus-model control final RMSE **14.01544 mm**, versus **14.28153 mm** for seasonal climatology and **14.89005 mm** for raw CFSv2. That is 1.86% improvement over climatology and 5.87% over raw. Independent metric implementations agree within 1.25×10⁻¹⁴ across the certified comparisons. This establishes executable attainability, not a published state-of-the-art reference or the maximum achievable skill. Do not select a new target after seeing pilot final scores.

Validity and ranking are already separate. Completion requires finite aligned arrays, nonnegative totals, the magnitude heuristic, reproducibility, input response, a causal probe, the trusted feedback ledger and the development-score claim. A valid forecast may score worse than either baseline; a low RMSE cannot rescue a failed validity gate. Prose questions are supplementary. At Level 2 the agent may state `development_rmse_mm: null` if unmeasured; otherwise the controller checks the score of the actual delivered development forecast within 10⁻⁴ mm. Five queries are an allowance, not a requirement. An attempt that uses none can still be valid, but it provides no evidence of a feedback-driven research loop.

The development scorer is appropriately narrow for this task: it freezes each requested Zarr store, checks and aligns the development coordinates, returns only aggregate development metrics and records hashes. Malformed accepted requests consume the allowance; subsequent calls are denied. Final scores and observations do not pass through this tool. Preserve candidate scripts and their score-store hashes so that the final candidate can be tied to actual experiments. The trusted ledger, not the agent's narrative, establishes the number and outcome of queries. A submitted development score must refer to the delivered forecast, which may differ from an earlier queried candidate.

Three existing validity limits require explicit code review before any strong interpretation:

- `responds_to_inputs` accepts movement anywhere in the delivered results. This template does not declare separate response groups, so changing development predictions can hide a cached final forecast. Check that **both** delivered splits come from the executed fitted procedure. This is a static gap inference, not a newly executed exploit.
- `no_future_information` perturbs forecasts from one cut in the middle of the final split. It can detect common whole-period normalization and smoothing leaks, but does not prove issue-by-issue causality, detect every within-half dependency, or test future information within development. Read candidate preprocessing, fit boundaries and feature construction. Using future forecast covariates to normalize an earlier forecast is still a leak even without observations.
- The magnitude rule requires each split's mean prediction to fall between 0.2 and 5 times the training observed mean. This catches common rate/total mistakes but is a heuristic, not a physical law for every valid forecast. The response rule also excludes completely input-independent forecasts. Describe validity as this task's contract rather than universal scientific validity. Investigate unexpected failures without retroactively changing this pilot's frozen grader.

The data notes also say target windows never cross split boundaries, while the final selector limits issue dates and does not apply a target-close restriction at the final end. Describe the selection as **2018–2021 issue dates**, rather than asserting that every verifying window ends before 2022. The archive was downloaded retrospectively in October 2026, original release vintages are not reconstructed, and its observations are public historical records. Private mounts and offline execution prevent direct access during an attempt; they cannot prove absence of model-training contamination.

Predeclare the following interpretation rules for one Luna and one Astra attempt with five development queries each:

1. Give both the same task, input bytes, ordinary dependency stack, documentation access, CPU/memory, token/time/tool limits and score allowance. Pin all files before launch. Record backbone and reasoning effort explicitly. Different backbones are two case studies, not stochastic replications. Keep all failures and query costs.
2. Check scientific completion first, then audit causal code and both-split dataflow. Report missing artifacts, runtime failures, malformed queries, false claims and invalid calculations by their actual cause. A budget-stopped attempt is not by itself a forecasting capability failure.
3. For valid forecasts, report raw final RMSE, both baseline scores, improvement versus each, and comparison with the fixed attainable control. Report development RMSE and candidate-selection history beside them. Do not choose the winner or revise the threshold using final feedback during the attempt.
4. If an agent improves development but loses to climatology on final, classify that as failed generalization on this split. If it is valid and improves both baselines, classify it as successful forecasting improvement under the pilot budget. Matching or beating the locked control is stronger local evidence, not a general state-of-the-art claim.
5. If both agents readily reach the control, stop treating this instance as a hard candidate. If Astra reaches it and Luna misses it with otherwise correct execution, record a candidate budget-dependent scientific gap. If both miss it, separate weak experiment selection, insufficient implementation time and weak signal before attributing difficulty. With one run per model and inspected historical targets, none of these outcomes establishes a hard capability boundary.
6. Keep spatial cells together in uncertainty analysis and respect overlapping weekly two-week targets. Report yearwise errors or temporal-block sensitivity; four final years do not support a precise stable ranking. Small deterministic score differences should remain descriptive. Any later replication or new holdout must be a separately declared experiment.

The most useful observations from this pilot will be whether each system establishes a valid baseline early, makes a few scientifically motivated changes, interprets development feedback honestly, preserves its best valid candidate, and generalizes. More elaborate code or exhausting all five queries is not success by itself. No new scientific requirement or template mutation is needed to learn that.
