# Issue a weekly rainfall forecast as observations become available

Forecast the rainfall total in mm for weeks 3–4 after each weekly issue, at nine grid cells in the south-western United States. Each target covers fourteen days, beginning fourteen days after its issue. Produce a finite, nonnegative prediction for every location at every issue. Your forecasting method is open.

This is a retrospective simulation of observation availability using historical CFSv2 forecasts and observed rainfall. The declared release times control when the program receives observations; they do not establish historical publication times or real-time data vintages. The controller advances through issues in time order. Your program may update from observations released during the evaluation period. It receives no unreleased observations or future forecast rows. Final observations and final scores are not exposed during development.

Write your program and `forecast-program.json` under `/work/submission`. The manifest contains only `argv`, a nonempty array of command arguments using relative paths for your retained code, for example `["python", "-u", "forecast.py"]`. The controller freezes the whole submission before evaluating a candidate. The same frozen program runs on the development episode and, after you finish, the final episode.

The controller launches one persistent process for an episode and sends JSON messages, one per line, on standard input. It first sends an `initialize` message containing `locations` and `training`. Each location has `id`, `latitude` and `longitude`. Each training record contains `case_id`, `issue_time`, `target_start`, `release_time`, `raw_mm` and `observed_mm`. Do not reply to initialization.

Each subsequent `forecast` message contains `case_id`, `issue_time`, `target_start`, `raw_mm` and `released_observations`. The latter holds the newly available observation records, with the same fields as the training records. Rainfall vectors follow the initialization location order. Reply with exactly `case_id` and `prediction_mm`, preserving the case identifier and supplying one finite, nonnegative rainfall prediction per location. Write exactly one JSON reply line for each forecast message. Standard output is reserved for those replies; diagnostics belong on standard error. Internal process state and scratch files under `/state` may persist within an episode; each evaluation starts afresh. The complete episode has a 120-second limit. Initial fitting and the first forecast may use the remaining episode time; each subsequent forecast reply has a five-second limit.

The tool `score_development` accepts the JSON manifest filename through `prediction_file`, for example `forecast-program.json`. It evaluates the frozen program with the same chronological release rules and returns aggregate development RMSE and fixed baseline scores. You have five development requests; a request reaching the evaluator counts even if the manifest or program is invalid. Development requests also consume the shared tool-call budget. Select your final program using development information only.

Forecast skill is measured by cosine-latitude-weighted RMSE across the complete declared issue and location support, with lower values better. Valid program execution and forecast skill are reported separately. No forecasting recipe, required library, or skill threshold is prescribed.
